# Hyd Tonight public UI review — 2026-10-11

**Verdict: changes needed.** The strongest part is the shared, pure filtering and HTML rendering. The weakest part is ownership of browser state and DOM lifetime. Adding more template helpers will not fix the focus loss, stale marker content, fallback failure, or inconsistent navigation. I recommend moving the reactive `/map` interface to small React components, rendering its initial content on the server and retaining the existing catalog/query/filter logic. This is a staged migration, not a new application framework or a public-site rewrite.

Reviewed the current working tree at HEAD `8bd0bfb`, including its existing uncommitted UI changes. Read `AGENTS.md` and `DESIGN.md` first. Source references below refer to that working-tree version, not just the committed diff. The admin was inspected only as a comparison.

## 1. Coherence: shared concepts, multiple implementations

### Keep these foundations

`filterCollection`, ranking, grouping, URL parsing and serialization already serve both environments (`src/web/map/client/filters.ts:38`, `:53`, `:96`, `:142`, `:172`). The server and client both use `renderPills` and `renderPanel` (`src/web/map/page.ts:36`, `:37`; `src/web/map/client/map.ts:258`, `:270`). Category emoji have one catalog owner (`src/catalog/category.ts:94`). Public map queries use `listable_event` and venue coordinates (`src/web/map/queries.ts:52`, `:64`). Preserve these boundaries.

### Architecture findings

1. **The same URL change has four different transition paths.** Marker selection updates filters, pushes history, renders, moves the camera, then sets the sheet (`src/web/map/client/map.ts:239`). Delegated links have separate regroup/open/recenter rules (`:285`). Forms construct a complete filter object from only the submitted fields and always fit the map (`:302`). Back/Forward only parses and renders (`:310`); it does not reconcile the sheet or reveal an offscreen selection. Consequently a venue restored by Back can be selected outside the current camera, and returning to the list can leave its old sheet detent. Fix: one transition owner with named actions for changing filters, grouping, selection and history restoration; derive camera/sheet effects from those actions, not from which DOM event produced them.

2. **The renderer is shared; its input semantics are not.** Server `rank(features, null)` lists all filtered venues (`src/web/map/page.ts:38`); the browser ranks only `inView` (`src/web/map/client/map.ts:250`, `:256`). Both render the heading “N events in view” (`src/web/map/render.ts:267`). The floating count counts every filtered feature, including approximate venues, and appends all-window unplaced events (`src/web/map/client/map.ts:265`, `:274`). The panel heading counts the viewport subset and is not a live region. Fix: explicitly distinguish all matching events, events in the unobscured map viewport, approximate venues and unplaced events. Supply a panel mode/count model rather than allowing a shared string to imply identical behavior.

3. **The DOM is being used as a second state store.** URL-backed filters live in `State.filters`, but drafts, filter disclosure, focus, image failure, poster detection, sheet detent and label visibility live in DOM nodes/attributes (`src/web/map/client/map.ts:20`, `:258`, `:325`, `:329`, `:408`; `src/web/map/render.ts:76`). Some survive recreation through manual copying; others disappear. The `pills: false` override exists specifically to preserve the range input during dragging (`src/web/map/client/map.ts:263`). Fix: give persistent components ownership of their local interaction state; keep derived presentation out of the application state.

### Concrete behavior drift

4. **Submitting either map form drops the chosen grouping.** `renderPills` retains `when`, `free`, category/area and search, but never emits a `group` hidden field (`src/web/map/render.ts:63`, `:70`, `:81`). Both native GET submission and the client submit parser reset `group` to `type` (`src/web/map/client/map.ts:306`; `src/web/map/client/filters.ts:48`). Probe: render pills with `group: "day"`; neither form contains `name="group"`. Preserve `group` in both forms; deliberately clear venue/event when changing filters.

5. **Marker cache identity does not describe its rendered content.** `put` returns immediately for an equal signature (`src/web/map/client/map.ts:172`). Venue signatures contain only selected state, event count and first category (`:205`), while `tileHtml` also renders the first event title and venue name in the label and accessible name (`src/web/map/render.ts:133`). Probe: search “Alpha”, then “Beta”, at one venue with two comedy events; each result has one event and signature `false:1:comedy`, but different tile HTML. The label retains “Alpha” while the panel shows “Beta”. Update the retained marker's contents from a stable event/venue identity, or compare the actual render inputs; do not use count/category as an event identity. Cluster IDs also need invalidation when the source changes: `:197` does not account for changed coordinates or a changed callback.

6. **Selection has representable but invalid combinations.** `MapFilters` permits independent venue/event strings (`src/web/map/client/filters.ts:21`). `withEventVenue` returns immediately whenever a venue already exists (`:90`). Thus `?venue=v1&event=nonexistent` remains unchanged; a real event from another venue is equally unreconciled. `selected` returns an array, but `renderPanel` consumes only its first item (`src/web/map/render.ts:260`). Normalize external URL input once against the data, then use `none | venue | event` selection alternatives with a required host venue for an expanded event. A resolved selection should be one feature, not an array of possible matches.

7. **The approximate-venue camera rule differs between click and reload.** `focus` correctly returns for approximate venues (`src/web/map/client/map.ts:159`), but startup calls `reveal` for any selected feature (`:442`) and forces a camera move (`:147`). Loading an approximate venue URL therefore moves to its area centre even though `DESIGN.md:416` says opening it should not move the map. Filter fitting also includes approximate area centres (`src/web/map/client/map.ts:138`). Use exact points for camera decisions and an explicit list-only path for approximate venues.

8. **The listing and map expose different filter meanings and lose context on switching views.** Listing filters include date range, source and max price; map filters use `when`, search and grouping (`src/web/types.ts:28`; `src/web/map/client/filters.ts:15`). “Map view” and “List view” link to bare paths (`src/web/pages.ts:236`; `src/web/map/page.ts:67`), losing even their shared category/area/free state. The listing's “Next 7 days” actually ends at `weekendTo` (`src/web/pages.ts:352`, `:381`). Probe on Sunday 11 October: `/?from=2026-10-11&to=2026-10-11`. Compute the promised date range and define a small translation for shared filters; explicitly indicate unsupported filters when changing surfaces.

9. **Public source links follow different boundary policies.** Detail uses `publicSourceUrl` (`src/web/pages.ts:246`, `:263`; `src/web/source-url.ts:2`), while the map copies `row.sourceUrl` and emits it directly after HTML escaping (`src/web/map/queries.ts:98`; `src/web/map/render.ts:213`). A legacy fixture containing `javascript:alert(1)` produces no such detail link but does produce a map `href`. Escaping is not URL parsing. Reuse the established public boundary and render a source action only for an accepted URL. The existing regression test omits `/map` (`test/site.test.ts:1137`). This establishes policy drift, not a browser exploit demonstration.

10. **Visual ownership is spread across three systems.** Map colors are generated roles (`src/web/map/tokens.ts:35`); listing colors and geometry are page literals (`src/web/pages.ts:435`); admin is Tailwind/shadcn with `.dark` and its own palette (`src/admin/ui/styles.css:5`, `:46`). Separate listing styles are explicitly allowed by `DESIGN.md:297`; do not classify their existence as a violation. However, the shared brand colors are repeated in listing CSS (`src/web/pages.ts:439`) and the favicon (`src/web/brand.ts:10`), while the map maps them to tokens (`src/web/map/page.ts:57`). Theme is shared publicly but implemented independently in admin (`src/web/theme.ts:29`; `src/admin/ui/components/theme-toggle.tsx:20`). Adopt shared public semantic roles for the brand/header first; do not import the admin's monochrome theme as the public design.

Other small duplications: `humanize` and escaping in `src/web/map/render.ts:17`, `:21` versus `src/web/pages.ts:344`, `:471`; date/clock formatting in `src/web/map/render.ts:96` versus `src/utils/time.ts:64`, `:83`; hand-coded theme SVGs in `src/web/theme.ts:12` versus generated map Lucide paths in `src/web/map/icons.ts:1`. Keep intentional formatting differences, but share date/clock parts and the icon source. Inline SVG paths are sensible for the current public bundle; replacing them with a whole client icon registry would be a regression.

### What recreation actually does

The panel is fully replaced on **`moveend`**, not every animation frame (`src/web/map/client/map.ts:429`, `:258`). Pills are **not** replaced on map movement; they are replaced on filter/selection/history render, except while the radius slider emits `input` (`:267`, `:369`). This distinction matters when estimating costs.

Delegated link/form/disclosure/image/sheet listeners are attached to stable ancestors (`:285`, `:302`, `:316`, `:325`, `:411`). They are not all rewired after replacement. Near me and slider handlers are the explicit exception (`:272`, `:361`). The fragility is node identity: focusing a group header and then panning destroys that header; selecting a row destroys the activated link; a filter/selection render discards an unsubmitted search draft and the filter popover's actual open state. Restoring `scrollTop` does not restore focus, selection or image state. Unconditionally scrolling `.row.open` into view can also override intentional scrolling on later redraws (`:260`).

Use a single normalized selection and a location union, not more optional fields. Make a resolved venue's event list nonempty at the query boundary; `tileHtml` currently asserts this only with `events[0]!` (`src/web/map/render.ts:130`), while the type permits an empty array (`src/web/map/types.ts:35`). Use the catalog `Category` type after parsing, instead of silently converting unknown internal categories to “other” repeatedly (`src/web/map/render.ts:131`; `src/catalog/category.ts:100`). Defaults for external URLs are a boundary policy; they should not become defaults for required internal component props.

## 4. Styling and polish

### Tokens: good colors, incomplete geometry ownership

`designTokensCss` generates role mappings once and caches them (`src/web/map/tokens.ts:113`). The dark mapping is centralized and respects an explicit light choice (`:124`). The CSS mostly uses those roles and spacing/radius/type variables. This is worth preserving.

The comment “every color, radius, spacing step and type style” is stronger than the enforcement (`src/web/map/styles.ts:2`). `test/mapTokens.test.ts:14` prohibits hex literals, not invented sizes, alpha values or undeclared variables. Many literals are documented in design prose and are legitimate: 64px event rows, 112px slider, border widths, the location pulse, camera margin. The maintenance issue is that some go through `LAYOUT`, others are copied into CSS/render templates, and the linter cannot prove that prose and code agree.

Concrete inconsistencies:

- Type/day headings use title **weight** with control **size/line-height** (`src/web/map/styles.ts:89`), while `DESIGN.md:518` requires title size. The emoji alone is forced to title size with `!important` (`src/web/map/styles.ts:91`). Venue headings also combine title weight/control font (`:77`). Use the `title` typography token for group headings, and intentionally choose the venue heading token; remove the compensating emoji override.
- The design specifies a 28px brand mark (`DESIGN.md:569`; `src/web/brand.ts:40`), but map-page CSS reduces it to 20px to fit a hard-coded 32px header/pill arrangement (`src/web/map/page.ts:58`). Wordmark styles introduce weight 700 (`src/web/brand.ts:48`) while the design's three-weight rule lists 400/500/600 (`DESIGN.md:594`). Document a brand exception or reconcile the hierarchy; don't keep shrinking the mark to patch overlapping layout.
- Thumbnail attributes hard-code 56px and cover attributes 400×225 (`src/web/map/render.ts:147`), while CSS uses front-matter size tokens (`src/web/map/styles.ts:114`). Change `event-thumbnail.size` and the attribute/CSS geometry diverges. Attribute dimensions and placeholder/skeleton geometry should come from the same component contract.
- The clear search action is wrapped in a submit form with a fixed-width input (`src/web/map/render.ts:66`; `src/web/map/styles.ts:46`, `:48`). Its appearance changes available space; persistent layout and declared clear-action geometry are preferable to adding another inline override.

### Specificity and layout hacks

Two `!important` rules are direct evidence of competing ownership: heading emoji size overrides inline `font-size` (`src/web/map/styles.ts:91`; `src/web/map/render.ts:32`), and hover/focus label visibility overrides declutter's inline visibility (`src/web/map/styles.ts:185`; `src/web/map/client/map.ts:234`). Dynamic `--tint`/`--ph` variables are appropriate data-to-style inputs; absolute skeleton positioning (`src/web/map/client/map.ts:47`) and hard-coded skeleton dimensions (`src/web/map/render.ts:294`) are layout rules disguised as rendering data. Use explicit component variants and a declutter class/attribute instead of fighting inline styles.

The global `.map-page a { color: inherit; }` has specificity 0,1,1 and defeats the lower-specificity `.link` color declaration (0,1,0) (`src/web/map/styles.ts:21`, `:27`). The stronger `.seg.on` and `.button.primary` declarations still win (`:64`, `:95`). Scope the anchor reset or give semantic link styling a consistent component selector; avoid making intentional green links depend on where they happen to inherit color.

Mobile `.pills` scrolls horizontally (`src/web/map/styles.ts:203`), while its filter form is a fixed-position popup (`:206`). Desktop pills reserve a card width and wrap (`:153`). These are two overlay-layout mechanisms with no common positioning/dismissal contract. Validate 720px boundaries and short viewports before calling the appearance premium. The map header's brand/list/theme controls have no wrap rule (`src/web/map/styles.ts:25`; `src/web/map/page.ts:67`), and the phone sheet has no safe-area padding despite `viewport-fit=cover` (`src/web/map/page.ts:48`; `src/web/map/styles.ts:208`). These are code-derived layout risks, not measured overlaps.

### Dark mode and motion

Map roles correctly follow both OS preference and explicit theme (`src/web/map/tokens.ts:124`). Repainting uses raw theme-specific basemap tokens rather than inverting colors (`client/style.ts:32`), and black music/film emoji get a documented light face (`src/web/map/render.ts:15`, `:133`; `src/web/map/tokens.ts:102`). The listing intentionally retains another visual system; its hard-coded brand copies are the drift risk, not the lack of Tailwind.

Map restyling is not protected by the startup catch: async `restyle` has no rejection handling or request-order protection (`src/web/map/client/map.ts:432`). Rapid theme changes can finish out of order; a base-style fetch failure can leave UI colors and map colors disagreeing. It also reloads the style on an OS change when an explicit choice means the effective theme did not change (`:433`). Track the latest effective theme, keep the existing map on failure, and reconcile only the final requested theme.

Reduced motion is mostly deliberate: camera functions check the preference (`src/web/map/client/map.ts:133`, `:139`, `:358`); sheet, tile, pills, rows, disclosure chevrons and skeleton/location animations disable motion (`src/web/map/styles.ts:219`). The sheet-height transition is still geometry-dependent: camera padding reads `offsetHeight` before a later detent change (`src/web/map/client/map.ts:127`, `:243`, `:244`, `:299`, `:300`). A resize/detent change has no padding reconciliation. Set the intended sheet state before computing settled layout, then keep padding synchronized with actual dimensions.

### Focus and touch targets

Most named controls have explicit focus rings (`src/web/map/styles.ts:58`, `:86`, `:97`); search has `:focus-within` (`:47`). The problem is preserving the focused node, not adding a ring to a node that is immediately destroyed. Theme and plain venue links are outside those focus selectors and rely on browser defaults.

44px targets are not consistently achieved. Preset pills get extended hit areas (`src/web/map/styles.ts:57`) and tiles get one (`:173`); filter summary is excluded and remains 40px. A group segment is approximately 26px high from its 18px line-height plus 8px padding (`:94`), native range has no minimum vertical target (`:41`), type/day summary has no minimum height (`:82`, `:89`), and the compact header theme toggle explicitly removes padding (`src/web/map/page.ts:62`). The detent buttons are correctly 44px (`src/web/map/styles.ts:214`). Use the `hitTarget` contract on all interactive controls rather than a selector exclusion list. Exact computed hit areas still require a browser pass.

## 5. Accessibility and interaction gaps

- **Map markers are already native buttons.** Do not report that keyboard activation is missing: `tileHtml` and `clusterHtml` emit `<button>` (`src/web/map/render.ts:133`, `:140`), and native keyboard activation reaches the delegated click. The gaps are unspecified ordering and unstable identity: `querySourceFeatures` determines creation order (`src/web/map/client/map.ts:190`), not ranked list order as required by `DESIGN.md:647`; signature changes remove the focused button (`src/web/map/client/map.ts:173`). Selection changes do not transfer focus into the panel or restore it on return (`:239`, `:285`). Keep keyed buttons and an intentional, tested focus route.
- **Marker names omit the category word.** Emoji are hidden, and the accessible name is next-event title, venue and “more events” (`src/web/map/render.ts:133`), not category. This differs from the design's named venue/count contract (`DESIGN.md:647`) and its category-as-emoji-plus-word principle (`:303`). Include the next event's category and a clear total count without requiring a user to interpret the emoji.
- **The map declares `role="application"` without an explicit interaction/help contract** (`src/web/map/page.ts:70`). That can change screen-reader interaction mode. Prefer a labelled map region and usable marker controls unless application mode is justified and tested. Keep the list as the equivalent route.
- **Event-row accessible labels hide useful row metadata.** `aria-label` is only the event title, overriding date, price and venue text in the link (`src/web/map/render.ts:210`); the thumbnail is correctly decorative. Preserve a title as the name and associate metadata as a description. `aria-expanded` has no `aria-controls` relationship to an expanded region (`:210`, `:213`). Associate that content and maintain focus on the activator; announce expansion without destroying it.
- **Sheet controls exist, but state is not communicated.** Expand/Collapse have names and native keyboard support (`src/web/map/render.ts:255`). They expose no controlled panel relationship, detent description or disabled end states (`src/web/map/client/map.ts:414`). At peek the result body remains an internally scrollable/focusable subtree; focus can scroll it without updating the detent. Define how focus opens the sheet and how closing returns to the originating marker/row. An always-available map panel should not automatically become a focus-trapping modal.
- **Sheet drag has incomplete pointer ownership.** It listens for global pointerup but neither captures the pointer nor handles pointercancel (`src/web/map/client/map.ts:416`). A canceled gesture can leave a handler waiting for an unrelated pointerup. Capture the initiating pointer, handle cancellation, and clean up the same gesture. Expand/Collapse remain essential alternatives to dragging.
- **Native details are a good starting point, but venue navigation and disclosure share a header.** A venue link sits inside `<summary>` alongside its disclosure hit area (`src/web/map/render.ts:249`, `:251`). Test keyboard and pointer routes for both actions, or separate them visibly. Type/day summary heights are small; don't replace native semantics with a bespoke accordion solely for styling.
- **Filters have no Escape/outside-click/focus-return policy.** The popup is a `<details>` form (`src/web/map/render.ts:76`), rebuilt with `open` whenever category or area is active. Closing an active filter popup is forgotten on the next render; denial opens it programmatically without focusing the area select (`src/web/map/client/map.ts:390`). Decouple “filter active” from “popup open”, retain the draft, and provide predictable dismissal and focus restoration.
- **The range input already has an accessible name and changing value text.** `aria-valuetext` and `<output>` are implemented (`src/web/map/render.ts:52`; `src/web/map/client/map.ts:368`). Retain that native control. Increase its target, keep it mounted, and announce settled results rather than every full count rebuild during dragging (`src/web/map/client/map.ts:369`, `:274`). Near me itself lacks `aria-pressed` and requesting/disabled feedback (`:375`, `:378`).
- **There is a count live region, but it does not describe map movement.** `#count` is `aria-live="polite"` (`src/web/map/page.ts:71`); `moveend` updates only the panel heading (`src/web/map/client/map.ts:429`, `:251`). Users are not told that viewport results changed. Provide a stable status node for viewport result changes, coalesced on move end; don't duplicate announcements between slider output, global totals and panel heading.
- **No-JavaScript/failure controls need honest visibility.** Near me has `hidden` (`src/web/map/render.ts:86`) but `.pill` declares `display:inline-flex` with no `.pill[hidden]` rule (`src/web/map/styles.ts:32`); author display styling can override the user-agent hidden style. Theme correctly has an explicit `[hidden]` rule (`src/web/theme.ts:46`). Add the equivalent visibility rule and verify that unavailable Near me is absent, not an inert button. The fallback probe also leaves sheet controls in the skeleton panel although startup never wired them.

## 6. Performance and resource lifetime

1. **Repeated panel reconstruction is the first cost to remove.** A filter render computes `visible()` at `src/web/map/client/map.ts:265`, again in `drawMarkers` (`:182`), again in `updateView` (`:250`), and again for selection (`:255`). It serializes all rows, destroys all their DOM and lazy images, restores scroll, then potentially requests smooth scrolling (`:258`, `:260`). `setData` can trigger further marker work, and a subsequent camera `moveend` rebuilds the panel again (`:275`, `:430`, `:429`). Compute the filtered collection once per state revision; derive viewport results from it and update only changed keyed sections/rows.

2. **Slider work is unbounded by frames.** Every `input` updates two GeoJSON sources, markers, decluttering and the entire panel (`src/web/map/client/map.ts:369`, `:275`). Keep the slider/output synchronous; coalesce map/result updates to an animation frame and commit the camera fit on `change`, as the code already intends (`:371`). Do not add URL history entries per slider tick.

3. **Marker churn exists despite the cache.** Stable signatures preserve elements, but selection/count/category changes call `marker.remove()` and recreate the holder (`src/web/map/client/map.ts:172`). Query-source tile changes also remove unseen entries (`:212`). Update stable venue elements in place; treat cluster identity as scoped to a source revision. Profile before moving every marker into React: a React wrapper does not make a large DOM-marker population free.

4. **Decluttering is worse than a simple pairwise loop.** It measures every tile/cluster, then interleaves visibility writes, computed-style reads and label rectangle reads (`src/web/map/client/map.ts:224`, `:230`). `owner(label)` scans all marker elements, and is recomputed inside each `solid.some` candidate (`:226`, `:233`); the nested scans can approach cubic work in marker count before early exits. Read all owner/box data once, decide visibility without DOM reads, then batch writes. Run once per settled movement/source revision. A spatial grid or MapLibre symbol collision handling is a later option only if profiling justifies it.

5. **Group accumulation repeatedly copies arrays.** `groups.set(key, [...existing, item])` copies the category/day group on each event (`src/web/map/client/filters.ts:177`), giving quadratic copying within a large group. Append to the existing group array. This is a small, readable fix; it is not a reason to introduce a generic grouping library.

6. **The bundle budget excludes a significant worker.** Main JS is about 295 KiB gzip, close to `DESIGN.md:662`'s 320 KB limit; main plus worker is 448,568 bytes gzip, before 10,739 bytes CSS, styles, tiles and event JSON. Worker loading is correctly separate (`src/web/map/assets.ts:53`). Keep this separation, measure total transferred bytes as well as the headline entry, and measure React's real incremental cost before adopting extra controls. The startup `Bun.serve`/asset response path declares no explicit compressed asset variant (`src/cli.ts:145`; `src/web/map/assets.ts:61`); a reverse proxy may compress, but that was not verified.

7. **Initial data is computed twice across requests.** Server renders it (`src/web/map/page.ts:26`), then the client fetches `/api/map` (`src/web/map/client/map.ts:48`) while removing the useful HTML. The API cache has a 60-second lifetime (`src/web/map/api.ts:16`) and may carry a different time snapshot from boot's windows. Send the initial snapshot as boot data, hydrate it, and refetch only when refreshing the window/data is useful. Continue reading `listable_event` and retaining venue-coordinate checks.

8. **Failure can be permanent rather than merely slow.** No timeout bounds the API/style awaits or map-load promise (`src/web/map/client/map.ts:48`, `:65`, `:436`); `skeletonMaxMs` is an animation duration, not a maximum loading duration (`src/web/map/styles.ts:139`; `src/web/map/layout.ts:64`). There is no map `error` listener to turn asynchronous tile/style failures into the documented list fallback. `?state=loading` intentionally never settles (`src/web/map/client/map.ts:49`), which is fine for QA but does not test the ordinary 1.5-second limit. Fix lifecycle behavior before optimizing animation.

These are source-derived risk estimates. No claims about actual frame rate, Android responsiveness or production tile latency are made.

## 7. Recommendation: React for the reactive UI, keep the server and pure model

**Choose a progressively enhanced React `/map` UI.** The current plain-string approach is defensible for static listing/detail pages. Here it is already maintaining component state by hand: remembered disclosures, scroll copying, image mutation, inline declutter state, pointer listeners and special-case rerender suppression. Stable React component identity directly addresses that recurring cost; changing only the CSS or adding more string “components” will not.

| Consideration | Keep strings + vanilla TS | React with server-rendered initial UI |
|---|---|---|
| No-JavaScript fallback | Existing GET forms and hrefs are valuable; startup currently breaks failure fallback. | Preserved if initial JSX is rendered on Bun and links/forms remain native. Copying admin's empty root loses it. |
| SEO and first paint | Server emits real event content today. | Equivalent when the same event components render on the server; `/e/<id>` and its JSON-LD remain the detail/SEO destination. |
| Bundle | Avoids React overhead, but MapLibre entry/worker dominate current bytes. | Adds React, wrapper and selected primitives; actual build must meet an explicit revised or retained budget. React is not a performance guarantee. |
| Maintenance | Can improve with a reducer plus keyed DOM updates, but that requires writing and maintaining the reconciliation/focus machinery. | One event/section/filter implementation with declared state and stable keys; hydration/data/style effects still require disciplined ownership. |
| Scope | Smallest immediate defect fixes. | Larger initial migration, feasible in slices; no need for Next.js, a full router or a catalog rewrite. |

The admin proves dependencies and Bun HTML imports are available, not that its boot method fits the public app: `src/admin/ui/main.tsx:4` uses `createRoot` on an empty shell; `src/admin/start.ts:38` serves that shell. For the map, render the initial UI with `react-dom/server`, then `hydrateRoot` matching components/data on the client. React requires the initial client/server content to match; do not immediately replace an all-results server list with a viewport-only client list before hydration finishes. [React hydration documentation](https://react.dev/reference/react-dom/client/hydrateRoot), [server rendering](https://react.dev/reference/react-dom/server/renderToString).

### Concrete choices

- **Rendering:** existing `react` / `react-dom` 19.3 dependencies, JSX components server-rendered by Bun. Keep the public response composition, existing routes and map-only asset delivery. No application framework migration.
- **Map wrapper:** `react-map-gl/maplibre`, retaining `maplibre-gl` and the explicit worker URL. Start by containing the current imperative map adapter while migrating the panel; wrap map/source/marker lifetimes afterward. Its current docs describe the MapLibre entry and v6 worker setup, but exact pinned compatibility still needs a build/runtime check before adoption. [react-map-gl setup](https://visgl.github.io/react-map-gl/docs/get-started).
- **State and URL state:** React `useReducer` for session-only location/sheet/disclosures and **nuqs** `useQueryStates` with `nuqs/adapters/react` for URL-backed filters/group/selection. Declare one shared parser/serializer descriptor, including the existing `free=1` contract, on the server-safe side; replace the old codec when switching rather than running both owners. Normalize venue/event relationships after parsing. nuqs supplies a plain React adapter and shared server loaders; its default is history replacement, so explicitly push navigation-like filter/group/detail actions. [Adapters](https://nuqs.dev/docs/adapters), [shared server parsers](https://nuqs.dev/docs/server-side), [history options](https://nuqs.dev/docs/options). No Redux, Zustand or query-cache library is warranted for one snapshot and these local states.
- **Component kit:** selected shadcn/ui **Radix** primitives, styled with the public `DESIGN.md` roles, plus the existing Tailwind 4 build tooling. Use Button/Input/Popover where behavior benefits; keep the native range and details initially. Prefer a **nonmodal shadcn Drawer backed by Vaul** for a snapping phone panel after validating its detents and scroll/focus behavior. The admin's `Sheet` is Radix Dialog, not a detent implementation (`src/admin/ui/components/ui/sheet.tsx:5`). Do not import `admin/ui` from `web`; the dependency rule forbids it. Extract genuinely shared primitives into an allowed module or give the public map its own narrowly scoped primitives. [shadcn Drawer](https://ui.shadcn.com/docs/components/radix/drawer), [Sheet](https://ui.shadcn.com/docs/components/radix/sheet), [Radix modal/nonmodal semantics](https://www.radix-ui.com/primitives/docs/components/dialog).

These are recommendations, not installed packages or measured replacement-bundle claims. A nonmodal drawer needs a focused compatibility/gesture check; do not silently substitute a modal overlay that disables the map. Reusing the admin's design palette would also be an unintended public visual redesign.

### Migration order

1. **Fix correctness on the current UI first:** retain server fallback until successful map startup, preserve grouping in forms, fix marker invalidation, normalize selection, and reuse accepted source URLs. Capture regressions for these exact scenarios; do not make them depend on migration completion.
2. **Define the normalized view model and update `DESIGN.md` before visual/behavior changes.** Separate URL-backed filters/selection from session-only location/disclosures/sheet state. Define all-matching versus viewport counts, approximate/list-only behavior, focus destinations, and component hit geometry. Keep the pure filters/grouping and current public query boundary.
3. **Convert panel, event row and image together to shared server/client React rendering.** Hydrate the same initial data snapshot; retain GET links and equivalent no-JavaScript content. Keep the current MapLibre adapter emitting settled viewport results. Remove panel `innerHTML` and image capture hacks as their React owners land; do not retain two live renderers for the same panel.
4. **Convert filter bar and URL transitions.** Move to the one shared nuqs descriptor and local reducer, preserving native forms and drafts. Cover reload, Back/Forward, modified-click navigation, group changes and denied/pending location.
5. **Convert mobile sheet and map lifetime.** Validate nonmodal Drawer detents, pointer cancellation, focus restoration and safe areas. Then adopt `react-map-gl/maplibre` for resource lifetimes; preserve clustering/worker setup and batch decluttering rather than translating the old loops verbatim.
6. **Polish and measure.** Reconcile typography, targets, header, focus, dark state and motion against design. Run the required 1280×800 and 390×844 light/dark state matrix (`DESIGN.md:660`), keyboard/screen-reader routes, and main-plus-worker transfer/performance checks. Keep `/` free of map JS (`test/mapPage.test.ts:100`). Broaden to shared public headers/listing metadata only after `/map` is stable.

If the owner declines the React cost, the minimum credible vanilla alternative is the same normalized transitions plus stable keyed panel/marker DOM and persistent filter/image/sheet controllers. That is achievable; simply reorganizing template strings is not enough.
